# Changelog

All notable changes to WinTraceForge are recorded here. The project follows [Semantic Versioning](https://semver.org/) for release tags.

## Unreleased

### Changed

- Reframed the project as a Windows security telemetry differential testing harness / lab focused on path-dependent security visibility: same operation or equivalent outcome, different implementation paths, and comparison of observable security evidence. Updated documentation, help wording, and assembly description while retaining current Defender Antivirus, ASR, and Firewall experiments and their existing CLI/lifecycle. No new execution experiments or behavior families are introduced.

### Added

- `wtf.exe firewall rule list [--store active|persistent] [--transport management|powershell]`: a strictly read-only inventory of the Windows Firewall rules in one policy store (`active`, the default, is the provider's `ActiveStore` view, without a claim about the GPO/MDM merge outcome; `persistent` is the machine-local store). Each rule shows its identifier, display name, enabled state, direction, allow/block action, profiles and reported policy source; disabled rules are listed and rules sharing a display name stay separate. Output opens with host, transport and store and ends with the total and an `Enumeration COMPLETE` status; the success result is the new `FIREWALL_RULES_LISTED`, never an ownership result. It uses its own default (`management`), supports only the two transports that can name the policy store explicitly (`com`, `native` and `cmd` are refused, never substituted; other firewall commands keep their defaults), needs no elevation and reports the real permission error if a read is denied. Enumeration goes through a new read-only `IFirewallRuleEnumerator` (no write method, separate from `IFirewallBackend` and from the `rule check` ownership path, and not routed through `ControlLifecycle`) that reads only each rule's direct properties, so a rule shape `rule check` would refuse is still listed. A value that cannot be read or decoded is shown as `Unavailable`/`Unknown(<raw>)` with a per-rule `READ LIMIT` note instead of being dropped; any failure once enumeration begins reports `Enumeration INCOMPLETE`, prints no rules or total, exits 1 with `FIREWALL_RULES_INCOMPLETE` and keeps the real error (labelled as a permission error when the read was denied), and zero rules is only reported after a successful enumeration. The powershell path emits a declared count, one Base64-encoded line per rule and a completion marker, and rejects a missing count/marker, a short or long stream, duplicate or out-of-range indexes and malformed lines as an incomplete list. Verified live (non-elevated) that both transports return the same rules for each store (613 active, 610 persistent, including 256 disabled; the three extra active rules are `Dynamic (ActiveStore)`), and that display names needed care: `MSFT_NetFirewallRule.DisplayName` is resolved for the request's WMI locale, System.Management defaults that to the thread culture while the cmdlets follow the UI language, so on a host whose user and system UI languages differ the same rules read as Chinese and English text until `management` requested the system UI language explicitly. `Build.ps1 -Integration` gains `--rule-list-read-only` (a read-only cross-check of both transports for both stores that never calls an add/remove path) and `Test-WinTraceForge.ps1` gains list smoke and usage-error cases.
- `defender asr` now supports `--transport com` and `--transport native` (in addition to the existing `management`), matching `defender exclusion`'s three-transport architecture: all three target the same `MSFT_MpPreference` class through a shared snapshot-assembly and single-instance-readback guard.
- `defender exclusion` and `defender asr` now both support `--transport powershell`, which invokes System32's own `powershell.exe` directly (an absolute path, not a bare name subject to CreateProcess search-order hijacking) and drives the `ConfigDefender` module's module-qualified `Add-MpPreference`/`Get-MpPreference` cmdlets instead of talking to WMI directly. The script is passed via `-EncodedCommand`, never written to a temp file first, and the child process' `PSModulePath` is restricted to the system module directory -- so neither the script nor the `ConfigDefender` module resolution can be substituted by another process running as the same non-elevated user (module-qualifying a call alone only guards against a same-named function/alias, not the module itself being shadowed from a user-writable `PSModulePath` entry). Every value that could ever contain caller-supplied or non-ASCII content -- exclusion values, ASR-only exclusions, error messages, readback results -- is Base64-encoded end to end, immune to the OEM/ANSI/UTF-8 codepage mismatches that would otherwise corrupt non-ASCII text or split a value containing an embedded newline into multiple values; a value containing an unpaired UTF-16 surrogate (which cannot be represented in UTF-8 at all) is instead rejected at CLI-parse time, identically for every transport. Every read script asserts `Get-MpPreference` returned exactly one instance and that each requested field actually exists before reading it, reads every field with a bare (unguarded) `foreach` rather than one gated behind an `if` (PowerShell's truthiness of a one-element array is that of its single element, so an `if`-guarded read would silently drop a rule whose action is the falsy byte `0`, i.e. `Disabled`), and reports an explicit success/failure marker rather than ever letting an incomplete or failed script read back as an empty snapshot. `Add-MpPreference` is a void cmdlet with no WMI return code, so a successful Add always confirms through readback (`MutationStatus.ApiUnknown`); a script that ends without either marker (e.g. torn down externally after the cmdlet may already have run) is classified the same way, not as a known failure, and its `stderr`/`stdout` is printed alongside the warning since that is often the only evidence of why. `defender asr`'s `powershell` backend reuses the shared `PowerShellRunner` process-execution helper introduced in `WinTraceForge.Defender.cs`, the same way its existing `com` backend reuses `DefenderModule.ComObjects`. An oversized Add request (too many/too long values for `-EncodedCommand`'s command-line budget) is rejected during `Prepare()`, before Connect()/Add() ever run, so the lifecycle reports `Mutation=NotAttempted` rather than misreporting it as `MutationStatus.ApiFailed`. The ASR `AttackSurfaceReductionRules_Actions` field is read back with an explicit `[int]` cast ahead of `[string]`, so a build that ever surfaces it as an enum-backed type rather than a plain byte reads back its numeric value, not its member name. The `PSModulePath` restriction is applied by temporarily overriding `wtf.exe`'s own environment variable around `Process.Start` rather than `ProcessStartInfo.EnvironmentVariables`, since that property's first access always copies the whole current-process environment into a case-insensitive dictionary and throws on a host whose raw environment already has two case-variant entries for the same variable (observed for `Path`/`PATH`); both `powershell` transports previously failed to even launch `powershell.exe` on such a host.
- `firewall` now supports `--transport management` (in addition to the existing `com` and `native`), targeting the WMI Firewall provider (`MSFT_NetFirewallRule` in `root\StandardCimv2`, the same provider PowerShell's `New-NetFirewallRule` uses) instead of the `INetFwPolicy2`/`INetFwRule3` COM interfaces `com`/`native` share. All three transports read/write the same persisted rule store through the same ownership schema and readback comparison, so a rule added with one can be checked or removed with any other; `management` looks a rule up by `ElementName` rather than `InstanceID`, since a rule created through `com`/`native`'s `HNetCfg.FWRule` gets an opaque provider-generated `InstanceID` with its netfw `Name` surfaced only in `ElementName` (confirmed by live cross-transport add/check/remove testing in both directions). `management`'s `profiles` command explicitly reads `PolicyStore=ActiveStore` rather than the default local/persistent store, matching `com`/`native`'s always-effective-policy semantics (confirmed live on a domain-managed host); its rule readback also refuses rather than silently misreports a rule secured with `Authentication`/`Encryption`/`OverrideBlockRules`, since this transport never creates such rules and always reports `SecureFlags=0`.
- `firewall` now additionally supports `--transport powershell` and `--transport cmd`. `powershell` shells to System32's own `powershell.exe` and drives the `NetSecurity` module's own cmdlets (`New-`/`Get-`/`Remove-NetFirewallRule`, the `Get-NetFirewall*Filter` family, `Get-NetFirewallProfile`) and the `NetConnection` module's `Get-NetConnectionProfile`, reusing `DefenderModule.PowerShellRunner`'s process-execution hardening (absolute path, restricted `PSModulePath`, `-EncodedCommand`, Base64-encoded values) and `ManagementFirewallBackend`'s raw-value codecs/normalizers wholesale rather than duplicating either (confirmed live: casting a filter/rule CIM-enum property to `[int]` yields the identical raw WMI value `management` already decodes, for every field this transport reads). Like `management`, it shares the full ownership schema and readback comparison with `com`/`native`, so a rule created by any of these four transports can be checked or removed by any other. `cmd` instead shells to `cmd.exe` and drives `netsh.exe`'s `advfirewall firewall`/`advfirewall` context (`cmd.exe /d /s /c "<netsh.exe> ..."`, `/D` disabling AutoRun and `/S` preserving netsh's own inner `name="..."`/`program="..."` quoting, the same nested-quoting shape `Build.ps1`'s own `Invoke-VcCommand` already uses), parsing the fixed-column text of `netsh advfirewall firewall show rule ... verbose` and `netsh advfirewall show allprofiles`/`currentprofile` rather than calling a typed API, and refusing outright on any unrecognized label (not every value is checked this way — `Program`/`Service`/`Description`/a single-value `RemoteIP` or port pass through as plain text, and a missing `Description:` line reads as `""` rather than being refused). `cmd` is **not** fully interchangeable with the other four transports: `netsh advfirewall firewall add rule` has no `group=`/`grouping=` parameter (confirmed against Microsoft's own documented parameter list), so a `cmd`-created rule can never carry this tool's `Grouping` ownership marker; `FirewallModule.ExpectedGrouping` returns `""` instead of `FirewallModule.Group` only for `--transport cmd`, so ownership for a `cmd`-created rule rests on Name+Description alone, and the other four transports correctly refuse it as a Grouping mismatch — check/remove a `cmd`-created rule with `--transport cmd`. `cmd`'s readback also reports `ExcludedInterfaces` as `"not available (cmd)"` rather than an empty list (netsh exposes no such field via any `show` command, so this is "not observed," not "confirmed none"), leaves `LocalAppPackageId`/`LocalUserOwner`/the three authorized-user-or-machine-list fields hard-coded empty (no corresponding netsh text field exists at all), refuses a comma-joined multi-value `RemoteIP` and any unrecognized readback label the same way `management` refuses an unsupported shape, and confirmed live that `netsh` displays a rule's raw WMI `Profiles` value of `0` ("Any"/unset) and an explicit `7` (Domain+Private+Public) identically as `Domain,Private,Public` text — immaterial for this tool's own rules (which always request an explicit nonzero mask) but a genuine fidelity gap reading a third-party rule through this transport. Also confirmed live: `netsh advfirewall show store` reports the `Local` policy store by default with no netsh command found to select the GPO-merged/`ActiveStore` equivalent the other four transports read for `profiles`, so `cmd`'s profile settings (not its rule add/check/remove, and not `CurrentProfiles`) can diverge from the other four on a GPO-managed host; and that `show rule` both matches and resolves a built-in rule's raw MUI `ElementName` to its display text, and expands a `%SystemRoot%`-style macro in a `Program` path — neither relevant to this tool's own rules. `BuildAddCommand` omits `program=` entirely for an unrestricted rule rather than sending the undocumented literal `"any"` as a path (`add rule ?` documents no `"any"` keyword for `program=`, unlike `localport=`/`remoteport=`), matching `com`/`management`'s existing "preserve unspecified defaults" behavior. `IFirewallBackend.Add()`/`Remove()` now return `MutationStatus` (`ApiSucceeded` or `ApiUnknown`) instead of `void`: `powershell`'s and `cmd`'s "no clear success marker" case reports `ApiUnknown` (deferring to the shared post-mutation `Verify()` readback, like `DefenderModule.PowerShellBackend.Add()` already does) instead of being silently reported as a confirmed `ApiSucceeded`; `cmd`'s `Remove` also re-checks for exactly one match immediately before its name-based `delete rule` call, mirroring `management`'s `RequireOne`-then-`Delete()` and `powershell`'s own count check, since netsh's delete has no per-object handle and would otherwise remove every rule sharing a name.
- Second review pass on the `powershell`/`cmd` firewall transports, each independently confirmed live before fixing: `firewall profiles` now prints a `Policy store` row (`Local (not GPO-merged effective policy)` for `cmd`, `Effective (GPO-merged)` otherwise) so the Local-vs-effective distinction is visible in the console output/log itself, not only in code comments and docs. `cmd`'s rule parser now treats a missing `Description:` line as `""` instead of a hard refusal (confirmed live: 21 of 606 real rules on one host omit it entirely, e.g. "Smart Connect" — the same "line absent" shape `Program:`/`Service:` already handle); the `--cmd-read-only`/`--powershell-read-only` candidate-probe loop also no longer aborts on a real rule name `CmdFirewallBackend.RequireSafeForCmd` legitimately rejects (found present among real rule names during the same sweep). `FirewallOperation.Verify`'s wording for an `ApiUnknown` mutation now says "outcome ambiguous; ... (not applied/not removed)" instead of "Add/Remove returned," which overstated what is actually known when the backend itself never confirmed success. The `netsh` output codepage fix now calls `kernel32!GetOEMCP()` directly instead of `CultureInfo.CurrentCulture.TextInfo.OEMCodePage`, which is the OEM codepage associated with the *culture*, not the machine's actual console codepage — confirmed live to diverge (a development host with `CurrentCulture=zh-CN` reported OEM 936, a double-byte codepage, from that property while the real system codepage was 437). The `cmd`/`powershell` outcome-classification logic (netsh exit/`Ok.` trailer; `WTF_*_OK`/`WTF_*_ERROR:` markers) and the `cmd`/`powershell` rule- and profile-text parsers are now pulled into pure, `internal`, directly unit-tested functions (`CmdFirewallBackend.ClassifyMutation`/`ParseRules`/`ParseAllProfiles`, `PowerShellFirewallBackend.ClassifyMutation`/`ParseRules`, and a new general-purpose `DefenderModule.PowerShellRunner.ClassifyResult` `ClassifyAddResult` now wraps) exercised against fixtures — several built from real captured `netsh`/PowerShell output — covering a rule with `Program`+`Service`, one with neither, a comma-joined multi-value `RemoteIP`, an unrecognized label, a missing `Description`, `show allprofiles`, and (for `powershell`) a truncated/out-of-range/mismatched marker stream, rather than relying solely on whatever rule shapes happen to be readable on the host running `-Integration`.
- Third review pass: the `--cmd-read-only`/`--powershell-read-only` candidate-probe loop's exception handling was narrowed back to catching only `FirewallReadbackUnsupportedException` (widening it to the `FirewallRefusalException` base type in the prior pass, to skip past a real rule name containing `%`/`!`, had also silently swallowed genuine output-format drift, e.g. a future Windows build spelling `Enabled: Yes` as `Enabled: True` — exactly the kind of regression this integration mode exists to catch); the candidate name itself is now pre-filtered for unsafe characters instead. `--powershell-read-only`'s candidates now come from `NetSecurity\Get-NetFirewallRule`'s own `DisplayName` values rather than the raw WMI `ElementName` (which frequently doesn't round-trip through the resolved-name-only cmdlet — see the prior pass's MUI-name note), so this mode now reliably exercises `PowerShellFirewallBackend`'s real script-to-parser contract end to end instead of reporting "skipped" on every run, confirmed live. `CmdFirewallBackend.FindByName`'s not-found/failure classification is now also a pure, unit-tested function (`ParseFindByNameResult`), and `FirewallOperation.Verify`'s `ApiUnknown` wording now covers the "readback found more than one rule" case, not just "found none," with the same "outcome ambiguous" phrasing.
- Fourth review pass: `--powershell-read-only`'s candidate-probe loop no longer treats a zero-match `DisplayName` candidate as an ordinary skip. Because its candidates are sourced from the exact same `Get-NetFirewallRule.DisplayName` property `PowerShellFirewallBackend.FindByName`'s own script filters by (unlike `--cmd-read-only`'s raw-`ElementName` candidates, which can legitimately miss due to MUI-name resolution), a zero-match result there can only mean the lookup itself regressed (e.g. back to filtering by `Name`); this now asserts loudly instead of silently reporting "skipped," and a skip is only accepted when every considered candidate was a genuinely unsupported rule shape. The success message also now says `DisplayName-keyed` for `powershell` rather than the `management`/`cmd`-only-accurate `ElementName-keyed`. Every script `PowerShellFirewallBackend` runs now starts with `Set-StrictMode -Version Latest`: without it, a property renamed or removed by a future `NetSecurity` module version would read back as `$null`/`0` rather than throwing, and for `Authentication`/`Encryption`/`InterfaceType`/`OverrideBlockRules` that would silently decode an actually-restricted rule as unrestricted instead of hitting the existing refusal — confirmed live (via a new regression test that runs a real `powershell.exe` against a deliberately-missing property) that `Set-StrictMode` turns that read into a terminating error even on a plain, strongly-typed object, not just a `PSCustomObject`. Also added a regression case pinning `FirewallOperation.Verify`'s "readback found more than one rule" wording, and fixed two inaccurate comments (one misattributing the `Policy store` console row to the wrong method, one describing two same-shape-but-different-name fixture blocks as "sharing a name").
- Fifth review pass: the prior pass's live-`powershell.exe` `Set-StrictMode` test proved the *language feature* works, but proved nothing about whether any of `PowerShellFirewallBackend`'s own six generated scripts still contain the line -- confirmed live by mutation testing (deleting `Set-StrictMode` from the `FindByName` script builder alone left the entire default `-Test` suite, including that same test, at a full pass; `--powershell-read-only` couldn't have caught it either, since every property name it reads happens to exist today). All six scripts' previously-inline `StringBuilder` assembly is now extracted into named, `internal`, directly callable builder methods (`BuildConnectScript`, `BuildCurrentProfilesScript`, `BuildReadProfilesScript`, `BuildFindByNameScript`, `BuildAddScript`, `BuildRemoveScript`) sharing one `ScriptPrologue` constant, and a new deterministic (no process spawn) regression test asserts every builder's output actually starts with it -- re-confirmed live that this test does fail on the same mutation that previously passed silently. Also fixed a comment that misdescribed `CmdFirewallBackend`'s multi-block rule parsing as splitting on the "----" separator line; it actually splits on a recurring "Rule Name" label, and merely skips the separator like any other unparseable line (the conclusion the comment was drawing -- that splitting doesn't depend on name equality -- was already correct, only the described mechanism was wrong).
- Sixth review pass: the prior pass's six `StartsWith(ScriptPrologue)` assertions all read their expected value from `ScriptPrologue` itself, so weakening the constant (e.g. quietly dropping `Set-StrictMode -Version Latest` back out of it, leaving only `$ErrorActionPreference = 'Stop'`) satisfied every one of them -- confirmed live by mutation testing (all 369 assertions still passed with the constant reduced that way). Added one assertion that instead pins `ScriptPrologue`'s actual content against a literal written directly into the test, independent of the constant; re-confirmed live that the same mutation now fails loudly and by name.
- Seventh review pass: `CandidatePowerShellDisplayNames` (the `--powershell-read-only`/`--cmd-read-only` candidate-probe loop's source of real rule names to look up) checked for its script's `WTF_LIST_ERROR:` failure marker but never for its `WTF_LIST_OK` completion marker before parsing `stdout` -- confirmed live by mutation testing that a script ending without either marker (simulated by renaming the emitted success marker) silently decoded as zero candidates, TransportReadOnly's loop then simply never ran, and the mode still printed "all were unsupported shapes; skipped" and exited 0, reporting the real-rule readback probe as a harmless skip when it had never actually executed. Now requires the completion marker exactly like every other script in this file already does, throwing instead of silently truncating; re-confirmed live that the same mutation now fails loudly (`... did not complete (exit 0): ...`) instead of reporting a false skip.

## 0.1.0 — 2026-09-25

Initial public release of WinTraceForge (WTF), a Windows x64 defense-control test harness.

### Added

- Defender Antivirus exclusion checks and controlled additions through managed WMI, COM Automation, and native WMI execution paths.
- Attack Surface Reduction (ASR) posture inspection, ASR-only exclusion checks and additions, single-rule action checks and changes, and a controlled behavioral verification command.
- Windows Firewall test-rule add, check, and remove operations through managed and native COM paths, plus read-only profile inspection.
- Existing Event Log collection and bounded raw ETW capture with module-specific correlation for Defender, ASR, and Firewall operations.
- `wtf.exe --version` and `wtf.exe -v`, with SemVer metadata in both `wtf.exe` and `WinTraceForge.Native.dll`.
- Automated Windows builds and non-mutating regression tests, including native Firewall `INetFwRules::Add` boundary coverage.
- Version-tagged release packaging with a Windows x64 ZIP, SHA-256 checksum, and signed GitHub build-provenance attestations.
- MPL-2.0 licensing and a security policy.

### Changed

- Standardized public branding as WinTraceForge (WTF) and organized managed and native sources by responsibility under `src/managed/` and `src/native/`.
- Introduced a shared control lifecycle for probe, mutation, verification, and restoration, with explicit read-only paths and cleanup guidance for persistent changes.
- Excluded generated binaries from the source branch; release binaries are distributed as GitHub Release assets.

### Known limitations

- ASR behavioral verification is experimental. Local process observation alone cannot confirm rule enforcement; inspect the correlated telemetry before drawing a conclusion.
- Defender exclusion and ASR rule/exclusion changes persist until manually restored. Firewall rules require the printed cleanup command and test ID for removal.
